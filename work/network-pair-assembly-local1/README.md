# Actual local network-pair assembly

The four command/installation roles were materialized in `../network-pair-assembled-local4` without starting Java, Gradle, graphics or a game. This is a source and launch-preparation result. It is not a successful client/server connection or a cold GitHub Actions reconstruction.

The preparation reuses the existing official NeoForge 21.1.219 production server `unix_args.txt` and the already verified ModDev client export. The server remains `forgeserver`; the client remains `forgeclientdev`. No fresh ModDev or NeoForm build is needed on this recovered machine. Both Unified roles use the unchanged source-owned FML assembler and validator. Their configured BOOT archives contain different installation policies appropriate to each side; the compiled FML base is identical. SERVICE, GAME and PRODUCT stay the exact render candidate, which is built/checked but game-unverified.

Each profile has the same built source-owned nonce probe and exactly three approved originals: EMI, Sophisticated Core and Sophisticated Backpacks. Native NeoForge uses the NeoForge EMI release; Unified uses the Fabric EMI release. Original JAR bytes are unchanged. Each Unified installation separately pins 46 embedded API archive records representing 47 logical API IDs. Those figures do not describe total platform archive closure.

The two clients explicitly use the approved virtual APILocal identity, token `0`, and `--quickPlayMultiplayer` to loopback ports 25631 / 25632. Each dedicated server has its own fresh profile, offline loopback listener, single-entry whitelist, empty ops, and disabled status/query/RCON. Both JVM recipes retain 1280 MiB heaps and two active processors. The unchanged aggregate memory gate and actual graphics preflight must still pass before any pair runs.

- All 33 locked original source/config/receipt inputs remained unchanged. Complete selected-mod configs and the required Unified Connector/Indigo platform configs were copied from accepted profiles. Client-only configs remain client-side. Complete server defaults are preseeded before world creation.

The original candidate and earlier profile/receipt evidence are untouched. Local1's static preparation failure is retained; the first native relocation helper incorrectly rewrote a legacy classpath prefix. The focused regression now preserves native `legacyClassPath` and `libraryDirectory`. Local2/local3 remain intermediate preparations; local4 carries the accepted target-specific initial packs and all required platform config files.

## Source and exact resources

`input-lock.json` pins every directly consumed source helper, official launch/tuple receipt, fixture receipt and accepted config resource. `required-text-inputs.json` maps exact bundled copies of the Python helpers and complete config text to their original relative paths. They are included to prevent losing a resource needed for recovery. Restore missing text only in a new consumer reconstruction; never overwrite an existing differing input. Third-party licenses accompany the corresponding preserved helper copies. Minecraft, dependencies and third-party mod JARs are not part of this source package.

The helper expects the recovered API1 installation, source tuple and existing fixture receipts at their recorded relative paths. Cold-runner installation/restoration remains a separate unproven prerequisite, with the prior exact dependency locks available. The approved own-probe binary and all twelve entries/resources/licenses are preserved in the separate nonce bundle.

Run `python assemble_pairs.py --output /absolute/fresh/output` from a reconstructed project only after verifying this source manifest and every input lock. It refuses an existing output. Run `verify_assembly.py --assembly /absolute/output --result-sha256 <actual-pin> --output /absolute/fresh/verification.json` for input and asset rehashing. These scripts never spawn a process.

## Remaining runtime preparation

1. An actual desktop or runner inventory and actual measured graphics preflight must bind the installed tools/libraries, owned display and renderer. The restricted execution-view Debian inventory cannot serve as an Ubuntu runner lock.
2. The reviewed supervisor derivative must preserve the prestart byte pin of `server.properties`, then compare its complete decoded values while recording host-written serialization changes. The frozen original supervisor would reject ordinary Java-properties comment/escape rewrites. All code/mod/config pins remain exact; whitelist/ops still need exact lifecycle observation.
3. The consumer must materialize its full immutable input closure and bind the actual graphics identity into the final supervisor spec. The official JDK has 205 legal-notice symlinks; the original supervisor's no-symlink tree grammar needs a transparent dereferenced consumer copy, preserving target bytes and provenance, before it can consume the full JDK. No canonical JDK files or modes were changed here.
4. A fresh native aggregate memory reading must satisfy 3,758,096,384 bytes plus the measured graphics reservation (at least 268,435,456). A source receipt cannot waive that gate.

No final runnable supervisor spec is fabricated without the actual graphics process/measurement. No GUI rendering, wire nonce roundtrip, client/server ownership or full API compatibility is claimed by this preparation.
